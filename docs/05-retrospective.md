# 复盘
## 最难的问题

最难之处是让“模型选择下一步”和“程序保证交付条件”同时成立。最初 Mock 可以稳定运行，但真实模型出现了不同问题：把单条事实误判为资料不足、漏问真正缺失的目标时长、采用受控清单外的文案，以及在脚本超时但仍可修复时直接结束。

这些失败说明，工具能用、离线流程能通，不等于模型能完成业务任务。实际 Trace 比成功截图更能定位问题：可以看到模型究竟读到了什么反馈、选择了什么动作、有没有真正重新检查。

## 修改与结果

先明确每个工具用途、输入缺失字段和受控表达范围，再收紧模型调用参数。strict 约束保证参数结构，但不保证业务判断正确；模型仍曾在超时后直接宣称失败。

因此增加结束门禁：按当前估时方法，目标仍可容纳一个最小分镜且尚未尝试修改时，拒绝直接宣称无法满足。门禁只返回问题，具体改稿由模型完成。真实超时路径最终从三个分镜、4.5 秒的第一版，改为一个分镜、1.5 秒的第二版，并重新通过两类工具检查。修复前记录完整保留。

## 工程取舍与收获

- 原生 Python 循环足够表达本题，不需要为了框架名称引入额外运行复杂度。
- 来源 ID 存在不等于事实被支持；需要同时检查声明文本和引用关系。
- 检查结果必须绑定具体脚本，改稿后要失效；不能把第一版检查贴到第二版上。
- Mock 适合验证错误处理、预算和状态，真实模型验收不可替代。
- 完成状态只说明当前检查通过，不代表文案质量、实际配音时长或长期稳定性。

## 当前不足与下一步

1. 正常样例仅 1.5 秒，未形成内容充实的 30 秒脚本。下一步应引入更多有来源的素材和更明确的时长区间，避免靠重复事实填满时间。
2. 受控句段检查牺牲表达自由。改进时应单独评估事实改写的支持关系，保持逐句来源和保守失败机制。
3. 单次真实运行不能给出可靠成功率。应固定评估集，重复运行并统计完成、事实错误、有效修正和预算消耗。
4. 工具失败的真实路径选择了结束。后续可以比较重试策略，但不能把重试写死后宣称是模型决策。
5. 1.5 秒结束门禁与估时规则耦合，改估时算法时须同步修改和验证。
