| --- | --- |
| Codex | 写了大部分代码和测试，执行了真实模型运行、离线复核和打包，起草了文档 |

代码不是我手写的。我的工作主要是定需求、看结果、做取舍、提验收要求。

## 我做了什么

**定需求和验收标准。** 我先按题目把核心链路排在前面：先让脚本生成和工具调用跑通，再补运行记录、真实模型验证和文档。中间我特别弄清楚了几件事：运行记录要包含什么、离线 Mock 能证明什么、不能证明什么，以及流程里哪些步骤是程序固定的、哪些应该交给模型决定。这决定了我验收时看的是实际输出和每一步的决策，而不只是程序能不能跑。

**根据评审决定改什么。** 最明显的问题是 30 秒脚本最后只剩一句“支持字幕”，检查是通过了，但这不是一份能用的脚本。我决定放开不涉及产品的叙事，同时对产品声明保持严格核对；超时用例里原来写了“先写三个分镜、超时就减少”，我要求去掉这类提示，换成普通的 30 秒请求，看模型会不会自己根据估时结果修改。中文提问、顶层素材来源、代码可读性这几处也一起改了。

**在检查方案上做取舍。** 发现编造的声明有漏检后，我先选了成本最低的办法：补词表。后来的评审用一批新句子证明补词表只对见过的句子有效，我就同意加语义复核。这一步让我意识到，修完已知的错例还不够，要用没参与修改的句子再测一遍才算数。

**要求补齐证据。** 语义复核加进来之后，我要求：

- 用新版本重新跑正常、超时修正、工具失败三条真实运行，并确认最终的语义复核结果确实来自模型的真实返回；
- 单独跑一次 36 句评估，不能拿三份成稿通过检查当作判定准确的证据；
- 评估结果如实记录，不针对留出集再去调规则；
- 把评估结果和代码版本对应起来，方便评审确认结果出自哪一版代码。

这些运行和核对都由 Codex 执行。

## 评审中发现的问题

问题和原因分析来自 Claude 的评审，是否采纳和怎么改由我决定，代码主要由 Codex 修改（语义复核那一项由 Claude 实现）。

| 问题 | 处理 |
| --- | --- |
| 30 秒脚本只有 1 个分镜、1.5 秒、一句“支持字幕”。原因是检查只认素材原文和几条固定短语，时长也只检查上限 | 不涉及产品的叙事可以自由写；产品声明仍需逐字对应素材并引用；时长改为 20–30 秒区间 |
| 超时用例把目标设成 3 秒，输入里写了先写三个分镜；模型是被程序拒绝后才修改的 | 改用普通 30 秒请求，去掉修改提示，保留所有尝试记录 |
| 工具报可重试错误时，模型直接放弃；无素材时没有换查询 | 在提示词里说明 `retryable` 的含义和检索无结果时的做法，重新运行 |
| 缺信息时，问题直接写成字段名 `target_duration_seconds` | 要求用中文问句，程序拒绝只写字段名的问题，并加测试 |
| 素材来源只写在各个分镜的 claims 里 | 输出增加去重后的 `source_ids` |
| `agent.py` 里有很多很长的条件判断 | 拆出 `RunState`、`contracts`、`prompts` |
| 在已正确引用“支持字幕”的分镜里写“剪辑时间直接减半”等编造说法，Claude 构造的 10 句里漏了 7 句 | 先补充风险词表（规则 2.2） |
| 补词表后，10 句已知的编造声明都能拦住；但换 12 句新句子只拦住 1 句，6 句正常叙事误拦 5 句 | 增加模型语义复核，建立开发集 / 留出集分开的评估集 |
