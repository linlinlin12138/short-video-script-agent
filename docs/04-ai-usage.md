# AI使用与贡献记录

## 使用范围

本项目使用两个AI工具：

- Codex：完成部分代码、测试、真实模型实验和文档的实现与执行。
- Claude：对提交做了多轮评审，指出下表中的问题；在第三轮直接实现了模型语义复核层、留出评估集及相关测试和文档（见下文“第三轮”）。

我主要负责理解题目要求、明确验收标准、参与多轮评审并决定修改方向。我借助 Codex 推进实现，也让 Claude 从评审角度检查代码和结果。下面区分我的判断与要求、AI 提出的具体问题，以及由 AI 完成的实现和验证。

## 个人贡献

我先围绕题目的核心要求安排实现顺序：完成脚本生成和工具调用，再补齐运行记录、真实模型验证和交付文档。过程中，我专门追问了实际运行记录应该包含什么、离线 Mock 能证明什么，以及 Agent 的流程哪些是固定的、哪些需要模型自己决定。这些讨论帮助我把验收重点放在实际输出和决策过程上，而不只看程序是否能跑通。

在结果评审中，我结合 Claude 的意见提出了具体修改要求。最明显的问题是，30 秒脚本最后只剩一句“支持字幕”，虽然检查通过，却没有可用的开场、分镜和收尾。我要求放开不涉及产品事实的叙事，同时保留产品声明与素材来源的严格核验；还要求去掉超时用例中暗示修改步骤的输入，用普通 30 秒请求观察模型是否会根据检查结果自行调整。对于中文提问、顶层素材来源和长条件判断，我也要求同步修正，让结果更容易阅读、代码更容易解释。这些问题的具体分析有 Claude 的帮助，修改代码主要由 Codex 完成。

我参与了检查方案的取舍。面对编造声明漏检，先采用补充词法信号的方案；后续评审发现它对新句子仍有大量漏检和误报，我接受了加入模型语义复核的改进。这个过程让我认识到，补齐已经出现的错误句子还不够，需要用没有参与修改的留出集验证。语义复核层和固定评估集由 Claude 实现，不能记作我独立编写。

在验证阶段，我要求用最新版重新运行正常生成、超时修正和工具失败三条真实路径，保存新的输入、输出和 Trace，并特别核对最终 `checks.semantic` 是否来自真实审核。我又要求单独运行 36 句固定评估，避免把三条成稿通过检查当成审核器准确的证明。本次语义层结果是 35/36；“做出爆款视频”仍漏检，同次还误拦了标题。我要求记录实际结果，没有继续针对这批留出数据修改规则来追求全对。

最后，我要求把新 Trace 与代码版本对应起来，补充源码快照、文件哈希和离线核对入口，便于评审确认结果对应哪一版实现。实际调用、快照生成和自动核对由 Codex 执行，我负责提出这些交付要求。版本清单是运行后补录的，文档也保留了这一限制，没有把它写成运行时采集的证据。

## 评审问题与处理

以下问题和根因分析来自 Claude 对提交的评审；我决定全部采纳，并要求 Codex 按下述方案修改：

| 评审指出的问题与根因（Claude） | 我的决定与修改结果（Codex 实现） |
| --- | --- |
| 创作者要求30秒脚本，正常输出却只有1镜、1.5秒和一句“支持字幕”，没有形成面向创作者的完整文案。根因是规则检查采用逐句精确白名单，同时只检查时长上限。 | 提出区分产品事实与非事实叙事：保留声明原文和引用核验，允许开场、创作情境、转场及收尾，对未引用文本扫描能力、效果、数字、比较和绝对化信号。本轮同时增加20–30秒区间检查，最终普通输入得到28.6秒、3镜脚本。 |
| 原超时用例设置3秒目标，并在style中要求先写三个分镜；模型被结束门禁拦截后才修改，难以证明自然决策。 | 要求改用普通30秒请求，去掉输入中的分镜数和修正指令，保留全部真实尝试。最终取得15.3→30.4→28.6秒的实际轨迹，模型自行扩写和压缩，全程无GUARD_REJECTED。 |
| 工具错误标记retryable=true，模型却直接放弃；无素材路径也缺少查询改写证据。 | 建议在系统指令中解释可重试错误的含义，并补充相关查询改写的验收记录。本轮分别取得临时错误后重试成功、两次检索无结果后请求补充的真实路径。 |
| 缺信息输出将target_duration_seconds字段名当成提问，读起来不像一句可以直接回答的问题。 | 要求使用自然语言问句，并在finish参数校验中拒绝仅返回键名的questions；增加相应回归测试。 |
| 素材来源只散落在分镜claim里，评审不便快速核对。 | 要求增加顶层去重source_ids，统一修改输出契约、结果组装及独立复核。 |
| agent.py包含多处很长的复合判断，模型决策与程序校验职责不便阅读。 | 要求拆分具名函数和状态逻辑；本轮形成RunState、contracts、prompts等清晰职责，保留版本失效、预算及完成门禁。 |


## 实际验证

第二轮评审中，Claude 构造了10句编造的产品声明，实测词法检查漏掉7句，并建议补充风险信号或增加语义复核。我选择先补词表，Codex 复现7/10漏检并补全规则2.2。

第三轮评审中，Claude 用另写的12句编造声明和6句正常叙事测试规则2.2，发现留出集只拦住1/12、误拦5/6，判断词表扩充已过拟合。经我同意，Claude 实现了：src/verifier.py 语义复核（判定模型逐句判定、程序校验判定结果）、check_rules 接入及完成门禁、风险信号在有判定模型时降为提示、data/eval/claim_eval.json 留出评估集与 run_claim_eval 评估脚本、相关测试和文档更新。当时尚未运行真实判定模型评估；后续36句真实评估已完成，结果与失败记录见03-evaluation.md。

以下是早期迭代的验证记录，不能代替后文的最新版真实重跑：

- 53项unittest通过，见examples/test-results.txt；原始工具、Mock与真实记录分别标记。
- 五类真实入口已更新，普通30秒请求出现15.3→30.4→28.6秒的模型自主调整，无GUARD_REJECTED；正常和超时入口复用同一执行，不重复计数。
- 七次自然时长开发采样及其他失败记录保留，未把成功样本选择说成稳定成功率。
- 临时错误真实重试恢复、无素材改写查询、缺信息中文提问均有记录。
- 独立复核来源、哈希、最终估时、顶层source_ids、输出schema和打包完整性；不提交密钥。
- 参考OpenAI官方函数调用和推理上下文文档；HTTP400由真实服务返回，之后使用Responses，未声称Chat接口已支持该组合。

## 固定评估集的真实语义审核

Codex 使用已配置的真实模型运行既有 36 句评估集一次，补充逐条落盘、进度和运行元数据，保存完整输入与工具返回。此次没有修改 Claude 编写的判定器、标签、词表和提示词。语义层与最终层均有 35/36 符合预期；留出集为 20/20，开发集“做出爆款视频”漏检，同次共用标题发生误报。全部 36 条 live 返回、数据哈希和各层统计均已核对；整体脚本被拦截没有被算成目标句检出。实际结果见 [评估报告](03-evaluation.md)。

随后，Codex 将原 Trace 和结果绑定到代码内容版本，保存逐文件哈希、完整源码快照和 Git 上下文，并编写离线核对入口。补录与运行时采集作了明确区分，原结果没有改写，也没有重新调用模型。当前源码一致性核对通过，临时篡改代码版本、Trace 哈希和模型配置的三种情况均被拒绝。
