# 方案设计

## 整体结构

没有用 Agent 框架，用 Python 标准库写了一个有上限的循环：每一轮模型从四个动作里选一个（检索素材、估算时长、检查规则、结束），程序执行工具，把结果交回模型，模型再决定下一步。

程序只负责三件事：校验参数、执行工具、守住完成条件。查什么、怎么写、怎么改、要不要重试、什么时候结束，都由模型决定。程序不会替模型改稿。

| 文件 | 作用 |
| --- | --- |
| `src/agent.py` | 主循环；`RunState` 记录当前草稿、检查结果和检索到的事实 |
| `src/contracts.py` | 输入校验、动作格式、工具的参数 schema |
| `src/prompts.py` | 系统提示词（带版本号） |
| `src/models.py` | 真实模型接入（Responses / Chat Completions）和离线 Mock |
| `src/tools/local.py` | 三个工具：素材检索、时长估算、规则检查 |
| `src/verifier.py` | 产品声明的语义复核 |
| `src/cli.py` | 命令行入口，保存输入、输出和 Trace |

选择不用框架，是因为这道题只有一个 Agent、四个动作，自己写循环更容易看清每一步谁在做决定，也方便在程序层面加完成条件。

## 工具

工具成功时返回 `{ok: true, result}`，失败时返回 `{ok: false, error: {code, message, retryable}}`。检索为空、检查不通过都算正常结果，不算错误。`retryable` 只是告诉模型这个错误可能是暂时的，程序本身不会自动重试。

每次工具返回时还会附上 `current_state`，告诉模型当前是第几版、哪些检查已经做过、还缺哪些，避免模型拿旧版本的检查结果当作新版本通过。

**素材检索**：把查询和素材的 ID、标题、关键词都做归一化后比较是否互相包含，按命中数排序。素材很少，所以没有做向量检索。

**时长估算**：中文按字、英文按词、数字按位计数。每个分镜的时长取旁白（每秒 4 个单位）和字幕（每秒 5 个单位）中较长的一个，最少 1 秒，再加 0.5 秒停顿。结果返回 `too_long`、`too_short` 或 `within_range`。程序不采用模型自己填的时长。

**规则检查**分两层，下面单独说明。

## 事实检查

### 第一层：引用和词法检查

- 每条 claim 的素材 ID、事实 ID 必须存在，原文必须和素材一致，并且出现在所在分镜的文字里。
- 品牌规则里的禁止示例（如“效率提升 80%”）直接拦截。
- 否定说法（“不支持字幕”）不能用肯定的事实来支撑。
- 去掉已引用的事实原文后，剩余文字如果出现能力、效果、数字、比较等词，就标记出来。

第一版检查只允许素材原文和几条固定短语，结果模型只能写出一句 1.5 秒的“支持字幕”。后来改成：不涉及产品的叙事可以自由写，只对出现风险词的句子做检查。

风险词表补过一次（规则 2.2），把评审中发现的 7 句漏检都覆盖了。但换一批没见过的句子测试后，编造的声明只拦住 1/12，正常叙事却误拦 5/6。继续加词只能修补见过的句子，所以加了第二层。

### 第二层：语义复核

`check_rules` 会把标题、画面、旁白、字幕逐句拆开，连同素材事实一起交给判定模型，要求它按固定的 JSON 格式列出每句中所有关于产品的说法，并标明是否有素材直接支持。

提示词定义了什么算产品声明：功能、操作方式、选项、效果、适用人群、和其他产品的比较，包括隐含的说法。也写明了“支持某功能”只证明支持这一点，不能推出它怎么实现或有什么效果。提示词里的例子没有用评估集中的句子。

判定结果不会直接采用，程序还会检查：

- 每一句都要有判定结果，缺了或重复了就当作判定失败；
- 判为“有支持”时必须给出真实存在的事实 ID，而且这个事实要在同一个分镜里被引用；
- 判定模型调用失败时，工具返回可重试的错误，由 Agent 决定重试还是结束，不会当成通过。

有了语义复核之后，第一层的风险词只作为提示，交给语义层判断，这样“我习惯先把文案同步到备忘录”这类句子不会被误拦。禁止示例、引用、原文和否定检查仍然直接拦截。如果没有配置判定模型，风险词照样拦截，而且 Agent 不能完成任务。

判定模型默认和生成模型相同，可以用 `OPENAI_JUDGE_MODEL` 单独指定。每次规则检查多一次模型调用，不计入 Agent 的工具次数。Mock 模式用固定标注代替判定模型。

## 版本和完成条件

估时和规则检查的结果都带有脚本的版本号和内容哈希。脚本内容一变，旧的检查结果就清空，而且必须升版本号。结束时程序会确认：最终版本的各项检查都通过、检查结果的哈希和最终脚本一致、引用的事实来自本次检索。最终输出里的时长由程序根据估时结果填入。

`finish` 动作还有几条限制：问题不能只写字段名、不能改用户的目标时长、在还没尝试修改的情况下不能直接宣布做不到。

## 模型接入

默认用 Responses API，也支持 Chat Completions。工具参数用 strict schema，每轮只允许一个动作。

改用 Responses 是因为实际测试时，gpt-5.4-mini 的 Chat Completions 接口不接受“函数工具 + low 推理”这个组合，返回了 HTTP 400。Responses 会把上一轮的完整输出原样传回下一轮，加密的推理内容只在内存里传递，不写入 Trace。参考了 [函数调用文档](https://developers.openai.com/api/docs/guides/function-calling) 和 [推理文档](https://developers.openai.com/api/docs/guides/reasoning)。

Trace 记录模型、API、推理设置、提示词版本和哈希、规则版本，以及每一步的动作、参数、返回和下一步，不记录密钥。
